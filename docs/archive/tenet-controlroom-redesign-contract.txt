TASK:
 Rebuild the Control Room so a person who has never seen TENET understands, in
 under 30 seconds: an AI agent wants to do something; TENET intercepts it; TENET
 checks who the agent is, what it may do, which policy applies and whether a human
 must approve; only then does the real request reach the external system; the
 receipt proves what happened. This is NOT a cosmetic pass. Order of work:
   T1 Diagnosis first: write docs/tenet-ui-diagnosis.txt naming each current
      defect with the exact DOM/text evidence. Then the target information
      architecture, the target data-flow model, and the API changes required.
      Then implement. Do not redesign blindly.
   T2 Identity/header: public name TENET (not WARRNT). Explanatory subtitle:
      "AI CONTROL LAYER — authority before action". Header explains the PRODUCT,
      not the implementation. `warrnt` only in internal identifiers.
   T3 First screen = ONE live action story, not a dashboard: AGENT -> REQUEST ->
      TENET CLASSIFIES (tool, action_class) -> AUTHORITY (warrant, actor) ->
      POLICY -> DECISION -> EXECUTION (upstream contacted: yes/no) -> RESULT ->
      RECEIPT. All values from the real record. No fixture in LIVE mode.
   T4 Data flow is the main visual story and every node is selectable; clicking a
      node shows its concrete evidence (POLICY -> policy id + matched rule +
      decision; UPSTREAM -> endpoint + request status + upstream_contacted +
      response metadata; RECEIPT -> receipt id + action id + run id + decision +
      execution result). This must be a real component, not a decorative SVG.
   T5 Agent panel states ROLE, ALLOWED actions, FORBIDDEN actions, AUTHORITY
      (warrant id), CURRENT ACTION, STATUS. The reader must learn who the agent is,
      what it may do and what it may NOT do.
   T6 Kill switch becomes contextual: inside the Action Inspector, next to the
      agent's authority ("REVOKE AUTHORITY"), not a standalone scary widget. After
      revoke: AUTHORITY REVOKED, pending/future actions BLOCKED, upstream NOT
      CONTACTED, receipt generated.
   T7 Proof panel answers "why can we trust this event?": ACTION -> POLICY ->
      DECISION -> UPSTREAM CONTACT -> EXECUTION -> RECEIPT with the concrete ids.
   T8 Action class is shown CONTEXTUALLY on the selected action ("this action is
      classified as read_external_data, and here is why that matters"), plus the
      boundary (internal/outbound). Never as a standalone taxonomy reference block.
   T9 HUMAN flow gets its own operator card: HUMAN APPROVAL REQUIRED, why, upstream
      NOT CONTACTED yet, [APPROVE] [DENY]; after approve -> decision allow, upstream
      contacted, execution; after deny -> decision deny, upstream NOT CONTACTED.
      This must be the real kernel flow.
   T10 "Explain this" control: a text control that renders an explanation DERIVED
      FROM THE AUTHORITATIVE RECORD ("Action A-0017 was denied because the agent's
      warrant does not include this tool."). Voice/TTS is an OPTIONAL enhancement
      and must never delay core enforcement, and must never invent an explanation.
   T11 Layout hierarchy: HEADER -> LIVE ACTION -> DATA FLOW -> ACTION INSPECTOR ->
      AUTHORITY -> HUMAN CONTROL -> PROOF. Story first, details second. The old
      six-independent-cards dashboard is not the entry experience.
   T12 Remove DEMO FEED from the main surface. A jury must never have to ask
      "is this the real system or a recorded demo?". The first screen answers that
      itself: LIVE -> action -> decision -> real upstream -> receipt. DEMO/fixture
      data may exist only behind an explicit, labelled mode.
